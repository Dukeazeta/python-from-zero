Borrowing tools with import

In real life

You don't forge your own hammer before hanging a picture; you take one from the toolbox. Python's toolbox is called the standard library, and import is how you take a tool out.

A module is a file of ready-made Python code. import loads one so you can use what's inside, written as module_name.thing.{{cite:1}}{{cite:2}} Modules that come with every Python installation are called the standard library.

tools.py
import math
import random

print(math.sqrt(81))          # square root
print(math.pi)
print(random.randint(1, 6))   # a dice roll: 1 to 6, both included
print(random.choice(["rock", "paper", "scissors"]))
Shows something like9.0 3.141592653589793 4 paper

Unlike range, random.randint(1, 6) includes both ends.{{cite:4}} The last two lines show different results each run; that's the point of random.

If you only need one thing, from math import sqrt lets you write sqrt(81) without the math. in front.

Try it: the long side of a triangle

Write hypotenuse(a, b) that returns the square root of a * a + b * b, using math.sqrt. For sides 3 and 4 it returns 5.0.

Try it: roll the dice

Write roll(sides=6) that returns a random whole number from 1 to sides. The tests roll it hundreds of times to check every result is in range and every face shows up.

Your own modules

In real life

A cook who keeps their best sauce recipes in a separate notebook can use them in any meal, instead of rewriting them inside every recipe.

Any .py file is a module. If shapes.py sits in the same folder as main.py, then main.py can say import shapes and use shapes.area(3, 4).{{cite:2}} This is how real projects stay organised: one file per topic.

One line you'll see at the bottom of many Python files:

shapes.py
def area(width, height):
    return width * height

if __name__ == "__main__":
    print(area(3, 4))      # runs only when you run shapes.py directly

It means "only run this part if this file was run directly, not imported".{{cite:3}} It's the right place for quick tests of a module's functions.

Installing packages, safely

In real life

A carpenter takes a separate toolbox to each job, packed with exactly what that job needs. Tools for one client's kitchen never get mixed up with another client's garden shed.

Beyond the standard library, people share hundreds of thousands of packages on PyPI, the Python Package Index. pip is the tool that downloads and installs them.{{cite:6}}

A virtual environment is the separate toolbox: a folder holding its own copy of Python and its own installed packages, usually one per project, so projects don't interfere with each other.{{cite:5}} Next you'll make one and install a small, silly package called cowsay.

{{os-switch}}

  1. Make a project folder and the environment. In the terminal, from your course folder:

    Terminal
    ...python-course> mkdir practice\cow
...python-course> cd practice\cow
...cow> python -m venv .venv

    This creates a hidden-looking folder called .venv with its own Python inside. It takes a few seconds and prints nothing. On Ubuntu or Debian, if it says ensurepip is not available, run sudo apt install python3-venv and try again.

  2. Install a package into it. Use the environment's own Python to run pip:

    Terminal
    ...cow> .venv\Scripts\python -m pip install cowsay

    The official tutorial also shows "activating" an environment so plain {{py}} uses it.{{cite:5}} On Windows PowerShell that can be blocked by a security setting, so thisThis course uses {{venv-py}} directly instead. It always works and you can always see which Python you're using.

  3. Use it.

    Terminal
    ...cow> .venv\Scripts\python -c "import cowsay; cowsay.cow('Hello from my venv')"
    Shows __________________ | Hello from my venv | ================== \ \ ^__^ (oo)\_______ (__)\ )\/\ ||----w | || ||

  4. See the toolbox wall. Now try the same with the ordinary {{py}}:

    Terminal
    ...cow> python -c "import cowsay"
    ShowsModuleNotFoundError: No module named 'cowsay'

    That's not a failure: it proves the package lives only in this project's environment. Whenever you see ModuleNotFoundError in a project, the first question is "am I using the right environment's Python?"

New words

Module
A file of Python code you can import.
Standard library
The modules that come with Python, like math and random.
Package
Shared code you install from PyPI with pip.
pip
The tool that installs packages: {{py}} -m pip install name.
Virtual environment
A project's own folder of Python and packages, usually .venv.

Check yourself

From memory, without scrolling up. A wrong answer here costs nothing: you just pick again.

1. Which numbers can random.randint(1, 3) return?

randint includes both ends, unlike range.

2. After from math import sqrt, how do you call it?

from ... import brings the name in directly, so you don't need the math. prefix.

3. Your project shows ModuleNotFoundError for a package you installed. Most likely cause?

Packages live in one environment. Run your code with that environment's Python, like {{venv-py}}.

4. When does the code under if __name__ == "__main__": run?

It's skipped when another file imports this one, so it's a safe spot for quick tests.
