Reading a longer error

In real life

A parcel's tracking history: "collected in Lagos, sorted in Ibadan, damaged in Ilorin". The last line is where things went wrong; the lines above show the route it took to get there.

When an error happens inside a function, Python's message, called a traceback, lists every function call on the way, oldest first ("most recent call last"). An error that happens while the program runs is called an exception.1

report.py
def average(numbers):
    return sum(numbers) / len(numbers)

def report(scores):
    print(f"Average: {average(scores)}")

report([])
ShowsTraceback (most recent call last): File "report.py", line 7, in <module> report([]) File "report.py", line 5, in report print(f"Average: {average(scores)}") File "report.py", line 2, in average return sum(numbers) / len(numbers) ZeroDivisionError: division by zero

(Newer versions of Python also draw ^ and ~ marks under the exact part of each line; they're left out here to keep it short.)

Read from the bottom: what went wrong (division by zero), then where (line 2, in average), then the route that led there (report called average, the main program called report with an empty list). The real cause is often a few lines up the route: here, nobody expected an empty list.

The usual suspects

ErrorUsually means
SyntaxErrorCode written wrongly: missing colon, bracket or quote
IndentationErrorBlock lines not indented as expected
NameErrorA name used before it was given a value, often a typo
TypeErrorWrong kind of value, like adding text to a number
ValueErrorRight kind of value, wrong content, like int("ten")
IndexErrorA list position past the end
KeyErrorA dictionary key that isn't there
ZeroDivisionErrorDividing by zero, often len() of something empty
AttributeErrorA method that doesn't exist for that type, like [1, 2].upper()

A calm way to hunt bugs

In real life

A mechanic doesn't replace random parts. They listen to the noise, make a guess ("probably the belt"), check that one thing, and only then fix it. Guessing and changing things at random makes it worse.

  1. Reproduce it. Find an input that makes the bug happen every time.

  2. Read the message, bottom up. If there's no error but the answer is wrong, compare what you expected with what you got.

  3. Make one guess about the cause.

  4. Check the guess by looking inside: print the variables at the suspicious point, for example print("DEBUG", i, total) inside a loop. Python's logging module is a tidier tool for bigger programs, but a temporary print is the quickest start.5

  5. Fix it, remove the debug prints, and re-test every case, not just the one that failed.

Handling the errors you expect

In real life

A trapeze artist works with a safety net. They don't plan to fall, but if they do, the net catches them and the show goes on.

Some errors aren't bugs; they're things you know might happen, like a person typing "ten" when you asked for a number. try / except is the safety net: Python tries the risky code, and if that kind of error happens, it runs the except block instead of crashing.23

ask_age.py
while True:
    try:
        age = int(input("Age? "))
        break
    except ValueError:
        print("Please type a whole number.")
print(f"Thanks, {age}.")
Shows (typed ten, then 21)Age? ten Please type a whole number. Age? 21 Thanks, 21.

Name the specific error after except, as above. A bare except: catches everything, including your own typos, and hides real bugs.

You can also cause an exception on purpose with raise, when your function receives something it can't sensibly handle: raise ValueError("age can't be negative").4

Testing your own code: edge cases

In real life

Testing a new bridge, engineers don't just drive one normal car over it. They try the heaviest lorry, an empty bridge in a storm, and traffic jammed bumper to bumper.

An edge case is an unusual but valid input at the extremes. Most bugs hide there. Before you call a function finished, try:

  • Empty: an empty list, an empty string.
  • One item: a list with a single number.
  • Zero and negatives.
  • Boundaries: exactly 18 when the rule says "18 or over" (Lesson 5).
  • Duplicates and ties.

A quick way to write your own tests is assert: a line that does nothing when its condition is true, and stops the program with an AssertionError when it's false.4 Put a few under your function in a .py file:

test_average.py
assert average([2, 4]) == 3
assert average([5]) == 5
assert average([]) == 0
print("All tests passed")

LeetCode does the same thing on a bigger scale: it runs your function against hidden edge cases. Thinking of them yourself first is how you get "Accepted" on the first submit.

New words

Exception
An error that happens while the program is running.
Traceback
Python's report of an exception and the chain of calls that led to it.
try / except
Run risky code, and handle a named error instead of crashing.
assert
A check that stops the program if its condition is false.
Edge case
An extreme but valid input, like an empty list.

Check yourself

From memory, without scrolling up. A wrong answer here costs nothing: you just pick again.

1. In a traceback, which line names the kind of error?

The last line names the error. The lines above show the route of calls that led there.

2. [1, 2, 3][5] raises which error?

Index 5 is past the end of a 3-item list.

3. Why name the error in except ValueError: instead of a bare except:?

A bare except also catches mistakes you didn't expect, like typos, and silently hides them.

4. Which is the best edge case to test for a function that averages a list?

An empty list makes len() zero, which would divide by zero. That's an extreme the normal cases never touch.
