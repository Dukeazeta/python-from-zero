A filing system labelled by content

In real life

Imagine a library where every book's shelf label is calculated from the book's exact words. Two identical copies always get the same label, so the library only ever keeps one. Change a single comma and the label is completely different. You can find any book instantly if you know its label, and you can check a book hasn't been tampered with by recalculating it.

Git stores every version of every file like that. A file's contents are turned into a 40-character ID by a hash function called SHA-1, and the file is saved under that ID. This is called content-addressed storage.2 The stored file is called a blob object. Those commit IDs like a60018f from Lesson 35 are the start of hashes too.

This project follows "Write yourself a Git", from the Project Based Learning list, which rebuilds Git's core in Python, together with the Pro Git chapter on Git's objects.126 Today: the blob, hashing, storing and reading back.

Bytes, not text

Hashing and compression work on raw bytes, not on Python strings. A bytes value is written with a b before the quote: b"hello". Convert text to bytes with "hello".encode() and back with .decode(). A byte with value zero, written b"\x00", is how Git separates the header from the content.

The blob format and its ID

Git doesn't hash the content alone. It first adds a short header: the word blob, a space, the content's length in bytes, and a zero byte. For content b"hello\n" (6 bytes), the full object is b"blob 6\x00hello\n". Its SHA-1 hash, written as 40 hex characters, is the blob's ID.23

Milestone 1: blob bytes and hash

Write blob_bytes(data) returning the header plus content, and hash_object(data) returning the 40-character hex ID, using hashlib.sha1(...).hexdigest(). The tests compare against IDs the real Git produces.

Stuck? A hint

The length is a number: turn it into text with str(), then into bytes with .encode(). Bytes join with + just like strings. For the hash: hashlib.sha1(blob_bytes(data)).hexdigest().

Where and how objects are saved

Git saves each object inside the repo's .git/objects folder: the first two characters of the ID name a sub-folder, and the other 38 name the file. So ce0136... lives at .git/objects/ce/013625030ba8dba906f756967f9e9ca394464a. Splitting by the first two characters keeps any one folder from holding millions of files.2

The file isn't stored as plain bytes: it's compressed with zlib, using zlib.compress(), and read back with zlib.decompress().24

Milestone 2: path, pack and unpack

Write object_path(sha) returning the path as a string with forward slashes. Write read_object(stored): decompress the stored bytes, split at the first zero byte, and return a tuple (kind, content), where kind is the header's first word as text (like "blob") and content is the bytes after the zero byte. blob_bytes is already written for you.

Splitting only once

raw.split(b"\x00", 1) splits at the first zero byte only, so content that itself contains zero bytes survives. Then header.split(b" ")[0].decode() gives "blob".

A command-line tool the real Git agrees with

Real tools take instructions from the command line: git hash-object hello.txt. In Python, the words typed after the script's name arrive in the list sys.argv: pythonpython3 mygit.py hash-object hello.txt gives ["mygit.py", "hash-object", "hello.txt"].5

  2. Write mygit.py with blob_bytes, hash_object, object_path and read_object, then this at the bottom:

    mygit.py (the end)
    import os
import sys


def write_object(data):
    sha = hash_object(data)
    path = object_path(sha)
    os.makedirs(os.path.dirname(path), exist_ok=True)
    with open(path, "wb") as f:
        f.write(zlib.compress(blob_bytes(data)))
    return sha


def main():
    command, filename = sys.argv[1], sys.argv[2]
    if command == "hash-object":
        with open(filename, "rb") as f:
            data = f.read()
        if "-w" in sys.argv:
            print(write_object(data))
        else:
            print(hash_object(data))
    elif command == "cat-file":
        with open(object_path(filename), "rb") as f:
            kind, content = read_object(f.read())
        print(content.decode(), end="")
    else:
        print(f"Unknown command: {command}")


if __name__ == "__main__":
    main()

    Three new tools here. open(path, "rb") opens a file to read bytes, and "wb" to write them; the with block closes the file for you afterwards. os.makedirs(..., exist_ok=True) creates the sub-folder if it's missing. Reading and writing files is covered properly in ATBS chapter 10.

Check yourself

From memory, without scrolling up. A wrong answer here costs nothing: you just pick again.

1. What does Git hash to get a blob's ID?

It's "blob", the size, a zero byte, then the content. Names and dates aren't part of a blob.

2. Two files with exactly the same contents but different names. Their blob IDs?

The ID comes from the contents only, so Git stores that content just once.

3. Where does the object with ID ab12... live?

The first two characters name the folder; the remaining 38 name the file.

4. With pythonpython3 mygit.py cat-file abc, what is sys.argv[2]?

sys.argv[0] is the script's name, [1] is "cat-file", and [2] is "abc".
