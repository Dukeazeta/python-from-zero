Binary search

On a sorted list you never need to look at every item. Check the middle, throw away the half that can't contain the answer, repeat. A million items take about 20 checks. Today you'll write it carefully, because small details like <= and + 1 are easy to get wrong.

Halve it, every time

In real life

"I'm thinking of a number from 1 to 100." Guess 50. "Higher." Now it's 51 to 100, so guess 75. "Lower." 51 to 74: guess 62. Each guess throws away half of what's left, so you never need more than 7 guesses for 100 numbers, or about 20 for a million.

Binary search finds an item in a sorted list by checking the middle and discarding the half that can't hold it.1 Each step halves the search area, so it's O(log n), compared with O(n) for checking items one by one (Lesson 19).

You keep two indexes, low and high, marking the part still in play, and compute the middle with mid = (low + high) // 2. The // operator is floor division: it divides and drops the decimal part, so 7 // 2 is 3.2 An index must be a whole number.

trace.txt
nums = [-1, 0, 3, 5, 9, 12], target = 9
low=0 high=5  mid=2  nums[2]=3   too small -> low = 3
low=3 high=5  mid=4  nums[4]=9   found at 4

The three details that trip everyone up

  1. while low <= high, with "or equal". When low == high there's still one item left to check.
  2. Move past mid: low = mid + 1 or high = mid - 1. You've already checked mid; keeping it can make the loop run forever.
  3. Sorted only. On an unsorted list the "throw away half" step throws away the answer.

LeetCode 704: Binary Search

Return the index of target in the sorted list nums, or -1 if it isn't there.3 It must be O(log n): the last test uses two million numbers and is checked thousands of times.

Stuck? A hint

Inside while low <= high: find mid. Three cases: equal, return mid; middle value too small, the answer is to the right, so low = mid + 1; too big, high = mid - 1.

Where would it go?

In real life

Filing a new folder in an alphabetical cabinet. Even if no folder has that name yet, the search tells you where it belongs: between the last folder before it and the first after it.

When binary search fails, low isn't random: it stops at the exact position where the target would be inserted to keep the list sorted. That's all LeetCode 35 asks for.4

LeetCode 35: Search Insert Position

Return the index of target if it's in the sorted list, otherwise the index where it would be inserted.

Stuck? A hint

It's your 704 solution with one change: what you return after the loop.

Challenge: binary search without a list

Binary search works on anything where "too small" and "too big" make sense in order. LeetCode 69 asks for the whole-number part of a square root, without using math.sqrt or ** 0.5.5 The possible answers 0, 1, 2, ..., x are already in sorted order, so search them: for a guess mid, if mid * mid is too big, go lower; otherwise go higher. Keep track of the last guess whose square fitted.

This idea, called binary search on the answer, shows up in many Medium and Hard problems.

LeetCode 69: Sqrt(x)

Return the square root of x rounded down to a whole number, using binary search. mySqrt(8) is 2 (because 2 × 2 = 4 fits but 3 × 3 = 9 is too big).

Stuck? A hint

If mid * mid <= x, mid could be the answer: save it, then look higher with low = mid + 1. Otherwise look lower.

Check yourself

From memory, without scrolling up. A wrong answer here costs nothing: you just pick again.

1. About how many checks does binary search need for 1,000,000 sorted items?

Halving a million down to one takes about 20 steps: O(log n).

2. nums[mid] is smaller than the target. What next?

The target must be to the right, and mid itself is already ruled out.

3. What is 17 // 5?

Floor division drops the decimal part of 3.4.

4. What does binary search require of its input?

Discarding half only works if order tells you which half can't hold the answer.
